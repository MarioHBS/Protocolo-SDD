# Estágio 05 — 4.5.0: nome do executável

**Tema:** dar ao CLI um nome que não colida com pacotes de outros ecossistemas.
**Depende de decisão do dono** (nome, reserva no npm, distribuição). Enquanto não houver
decisão, este estágio fica fechado e não segura os anteriores. O item R3-01 (4.3.0) já resolve
o problema imediato ("o agente não sabe invocar o CLI") com o nome atual.

## Contexto

P2/IP-003: o nome `sdd` existe no npm e `npx sdd` executou código de terceiros. O texto de
R3-01 é a defesa real; renomear e reservar o nome fecha o risco de squatting e de palpite de
`npx`. O nome candidato é `sddkit` (distintivo e fora do vocabulário do npm); `sdd-cli`
combinaria com o nome do pacote, mas é mais genérico. **Não foi verificado se algum deles está
livre no npm.**

## Custo medido nos projetos

`.sdd/`, manifesto, constituição, stages e hooks de caminho **não mudam**. Os arquivos
gerenciados (README, skills, templates, shims) são reescritos pelo `sdd update`. O que custa é
o que pertence ao projeto e não ao kit:

| Projeto | Permissões `Bash(sdd …)` | Menções em `CLAUDE.md` |
|---------|--------------------------|------------------------|
| P5 | 16 (8 em Bash e 8 em PowerShell) | sim (regra do registro de atritos) |
| P2 | ≥ 5 (inclui `sdd docs *`) | sim (regra sobre `npx`) |
| P4 | 5 (inclui `sdd docs *`) | não |
| P1, P3 | 0 encontradas | — |

Mais o hábito e os testes do próprio `sdd-cli`, que invocam `sdd`.

## Itens

### N-01 — Segundo entry point com o nome novo

- **Status:** planejado (depende da decisão)
- **Solução provável:** uma linha em `[project.scripts]` do `pyproject.toml`, apontando para
  `sdd_cli.cli:main`; nome vindo de `CLI_NAME` (R3-01, estágio 4.3.0).

### N-02 — `sdd` como alias deprecado

- **Status:** planejado
- **Solução provável:** ao ser chamado como `sdd`, imprimir uma linha de aviso em `stderr` e
  executar normalmente. Remover só na v5, junto com `sdd docs` (já marcado para sair nela).
  O aviso vai para `stderr` para não quebrar quem lê a saída.

### N-03 — Textos gerenciados com o nome novo

- **Status:** planejado
- **Solução provável:** shims, README e skills passam a dizer "`<novo>` é um binário Python no
  PATH; nunca use `npx` nem `npm`". Propaga por `sdd update`. Como R3-01 já usa `CLI_NAME`, é
  uma troca em um lugar.

### N-04 — `doctor` detecta o nome legado; `fix` reescreve

- **Status:** planejado
- **Solução provável:** nota `legacy_cli_name` quando `sdd ` aparece em `CLAUDE.md` ou em
  `.claude/settings*.json` do projeto (arquivos que o `update` não toca); `sdd fix` propõe a
  reescrita, com prévia. Cobre também `sdd docs`. Cuidado: reescrever permissões de agente é
  mudança de política de segurança do projeto; mostrar o diff e pedir confirmação.

### N-05 — Reserva do nome e decisão de distribuição

- **Status:** decisão em aberto
- **Contexto:** hoje o kit se instala da pasta ou do repositório (`pipx install .`); a decisão
  entre PyPI, npm ou só GitHub segue em aberto. Reservar o nome no npm evita que outro
  registre o pacote e o `npx <nome>` do agente execute código alheio.
- **Solução provável:** decidir a distribuição primeiro; só então reservar. Não migrar sem
  pedido explícito do dono.

## Sequência sugerida

1. Decidir o nome e conferir disponibilidade (npm, PyPI, buscas gerais).
2. N-01 e N-02 numa release; N-03 na mesma release (texto).
3. N-04 na release seguinte, depois de o alias estar em uso, para o `doctor` não acusar
   todos os projetos antes de o dono poder agir.
4. Varredura dos projetos que têm menções (P5, P2, P4). Em P4 ela cabe na própria migração
   para a versão vigente.
